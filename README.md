# Memorables

Pick a genre of date, a location, and a time window - Memorables finds real
venue types, sequences them into a day, checks that each one is actually open
at the time it'll be visited, factors in travel time and a buffer between
stops, and hands you a finished itinerary with booking links and calendar
export.

## Running it

```bash
npm install
npm run dev
```

Open the printed local URL. No API key or account is required - it runs
entirely on realistic mock venue data out of the box (clearly labeled "Demo
mode" in the UI).

## Deploying to Vercel (recommended)

The repo is Vercel-ready:

1. Push this branch to GitHub (already done if you're reading this there).
2. On [vercel.com](https://vercel.com), "Add New Project" -> import the
   `Memorables` repo. Vercel auto-detects Vite; no build settings needed.
3. In the project's **Settings -> Environment Variables**, add
   `GOOGLE_MAPS_API_KEY` (note: **no** `VITE_` prefix) with your Google key.
4. Deploy. Done - you get a permanent URL that works on your phone,
   including real geolocation (HTTPS is required for that, which Vercel
   provides).

In production the key never reaches the browser: the app calls the
serverless functions in `api/google/*`, which attach the key server-side and
forward to Google. That means you don't need (and shouldn't set) any
`VITE_GOOGLE_MAPS_API_KEY` on Vercel.

Saved itineraries sync through Supabase automatically - see "Cloud sync"
below.

## Cloud sync & sharing

Saved itineraries are stored in a Supabase project. The table has row-level
security enabled with **no** policies, so the Data API can't touch it; the
only access path is four `security definer` RPC functions, each requiring an
unguessable per-user sync key (a UUID minted on first use and kept in
localStorage - effectively a bearer token).

- **Cross-device sync**: History -> "Sync devices" shows your code; paste it
  on another device to share one history.
- **Share links**: after saving, the Share button copies a
  `?share=<id>` URL anyone can open (read-only view of that one itinerary).
- **Offline**: if Supabase is unreachable the app falls back to
  localStorage and says so in the History screen.

## Going live with real venues (local dev)

Copy `.env.example` to `.env.local` and set `VITE_GOOGLE_MAPS_API_KEY` to a
key with **Places API (New)** and **Routes API** enabled in the Google Cloud
Console. Restrict the key by HTTP referrer before using it anywhere public -
this is a client-side app, so the key ships in the browser bundle.

Once set, venue search uses live Places data (ratings, real opening hours,
websites) and travel times use the Routes API instead of straight-line
estimates. If a live call fails for any reason (bad key, quota, network), the
app silently falls back to mock data for that request rather than breaking -
you'll see a small "showing demo data" notice when that happens.

## How an itinerary gets built

1. **Location** - current position via the browser's geolocation API, a
   place search (geocoded through Places API when a key is set), or one of a
   few demo cities in mock mode.
2. **Preferences** - a genre (Romantic, Foodie, Adventure & Outdoors, Culture
   & Arts, Nightlife, Chill & Relax), a date, a start/end time window, how
   many stops, party size, a budget cap ($-$$$$), a travel mode, and how
   much buffer time to leave between stops. A free Open-Meteo forecast is
   shown for the chosen date; if it's rainy enough, outdoor stop types are
   swapped for indoor ones automatically.
3. **Building** - each genre maps to an ordered template of stop categories
   (e.g. Romantic/3 stops -> scenic spot, fine dining, dessert). For each
   category the app fetches nearby candidates, then greedily walks the
   sequence: for every candidate it computes real travel time from the
   previous stop, adds the buffer, and finds the earliest time the venue can
   actually take that visit - waiting for opening time if the venue isn't
   open yet (e.g. a dinner reservation naturally lands after 5pm even if the
   day started at noon), and flagging it if that wait or the total plan runs
   long. Three distinct options are generated by varying the starting venue
   and preferring venues not already used in another option.
4. **Picking & tweaking** - choose one of the three itineraries, then swap
   any single stop; everything after it is recomputed so times stay
   consistent.
5. **Booking & calendar** - each stop gets real deep links (the venue's own
   site if known, plus an OpenTable search for restaurants or a Viator
   search for activities/culture, plus a Google Maps link) and a one-click
   "Add to Google Calendar" link. The whole day can also be downloaded as a
   single `.ics` file with one event per stop.

## What "booking" actually means here

There is no generic public API that checks live availability and completes a
reservation across restaurants, activities, and venues - that requires a
signed partner integration per provider (OpenTable Partner API, Resy API,
Viator affiliate/partner API, Eventbrite, etc.), each gated behind a business
agreement. So this app does the part that's realistic to automate end-to-end
- discovery, scheduling, and travel-time-aware sequencing - and hands off the
final confirmation step to a real, working link to the venue's own booking
page. If you get access to a specific partner API, `src/services/bookingLinks.ts`
is the place to wire in a true one-click reservation for that category.

## Architecture

```
src/
  types/domain.ts          core data model (Venue, ItineraryOption, etc.)
  data/genres.ts            genre -> stop-category sequence templates
  data/venuePool.ts         mock venue templates (used in demo mode)
  data/demoLocations.ts     preset cities for demo-mode location search
  services/places/          venue search: mock provider + Google Places (New)
  services/travel/          travel time: mock estimator + Google Routes API
  services/itineraryBuilder.ts   the scheduling algorithm
  services/bookingLinks.ts  per-venue booking/search deep links
  services/calendar.ts      .ics generation + Google Calendar links
  services/storage.ts       localStorage persistence for saved itineraries
  components/               step-by-step UI (location, preferences, options, final, history)
```

Live data sources and mock data sources share the same interfaces
(`PlacesProvider`, `TravelProvider`), so the rest of the app never needs to
know which one is active.

## Known limitations / natural next steps

- **Geocoding free-text search** only works in live mode (it reuses the
  Places API); demo mode is limited to the preset city list.
- **Single calendar day** - the planner assumes one date within one calendar
  day; it doesn't currently plan multi-day trips.
- **Google API CORS** - the Places/Routes calls are made directly from the
  browser per Google's documented client-side usage. If you hit CORS or
  quota issues in practice, the fix is to proxy those two calls through a
  small server function (e.g. a Supabase Edge Function) instead of calling
  Google directly from the client.
